# Канон иерархии

Единственно допустимый формат дерева, правила нейминга, роли и исключения. Дерево — источник истины для всех производных артефактов.

## Что такое декомпозиция

Иерархическое разбиение функционала на составляющие («матрёшка»): модальное окно → элементы в нём → вложенные элементы и так далее. Цель — чтобы в визуальной схеме тестировщик видел покрытие кейсов.

## Формат дерева

- Отступ задаётся **табуляцией**; глубина — числом дефисов после табуляции:
  `-` (1-й уровень), `--` (2-й), `---` (3-й), `----` (4-й) и так далее.
- **Запрещены** символы дерева `├──`, `└──`, `│`, `┌` и любые ASCII-box.
- **Запрещено** оформлять отступы только пробелами без дефисов.
- Контейнер (есть внутренние элементы) помечается `(+)`. Конечный элемент — без пометки.
- Каждый уровень содержит **только непосредственных потомков**.
- Раскрытие выполняется **до полного раскрытия** («до конца матрёшки»).

### Схема уровней

```text
Корневой контейнер (+)
	-Дочерний элемент 1 уровня
	-Дочерний контейнер 1 уровня (+)
		--Дочерний элемент 2 уровня
		--Дочерний контейнер 2 уровня (+)
			---Дочерний элемент 3 уровня
			---Дочерний контейнер 3 уровня (+)
				----Дочерний элемент 4 уровня
```

### Правильный пример

```text
Открытый виджет (+)
	-Опция настройки виджета (+)
		--Открытие модального окна настроек. (+)
			---Опция включения / выключения звуков уведомлений.
			---Опция включения / выключения уведомлений.
	-Отображение иконки выключенного звука.
	-Опция закрытия виджета
	-Опция поиска. (+)
		--Отображение подсказки "Поиск чатов".
		--Отображение иконки "лупа".
		--Активация опции поиска. (+)
			---Отображение найденного чата. (+)
				----Отображение названия чата.
				----Переход в найденный чат.
			---Отображение подсказки "Ничего не найдено".
```

### Неправильный формат (не использовать)

```text
Открытый виджет (+)
├── Опция настройки виджета (+)
│   └── Модальное окно настроек (+)
└── Опция поиска (+)
```

## Что считается контейнером `(+)`

Модальные окна, страницы, формы, блоки, секции, вкладки, таблицы, списки, карточки, аккордеоны, меню, выпадающие списки, элементы списка и **любые элементы со своими элементами**.

## Что считается конечным элементом

Текст, заголовок, описание, label, иконка, изображение, чекбокс, радиокнопка, кнопка, поле ввода, ссылка, подсказка, отображаемое значение, статус.

## Правила разбиения

- Не объединяй разные сущности. Неправильно: `Поле имени`. Правильно: `Блок "Основные данные" (+)` → `Поле "Имя"` → `Placeholder`.
- Если список содержит несколько типов объектов — каждый тип отдельным элементом (`Активный ребенок`, `Неактивный ребенок`, `Новый ученик`).
- Разный внешний вид или разная бизнес-логика → разные объекты, даже если визуально рядом.
- Не смешивай уровни (поле внутри формы — только под формой).
- Именованные сущности — в кавычках: `Модальное окно "Заключение договора"`, `Кнопка "Заключить договор"`, `Ссылка "Перейти"`.

## Нейминг «Отображение …» (обязательно)

Префикс «Отображение …» обязателен для отображаемых состояний, текстов, значений, заглушек, статусов, счётчиков, превью, иконок, placeholder. Смысл: название отвечает на вопрос «что именно смотрит тестировщик на экране», а не «что хранится в данных».

| Неправильно | Правильно |
|---|---|
| `Значение "9+"` | `Отображение значения "9+"` |
| `Заглушка "Ничего не найдено"` | `Отображение заглушки "Ничего не найдено"` |
| `Строка поиска` | `Отображение строки поиска` |
| `Счётчик непрочитанных диалогов` | `Отображение счётчика непрочитанных диалогов` |
| `Название чата` | `Отображение названия чата` |
| `Статус "Онлайн"` | `Отображение статуса "Онлайн"` |
| `Текст сообщения` | `Отображение текста сообщения` |
| `Иконка "Без пушей"` | `Отображение иконки "Без пушей"` |
| `Placeholder "Поиск чатов"` | `Отображение placeholder "Поиск чатов"` |

**Не переименовывай насильно** интерактивные действия и контейнеры: `Кнопка "Отправить"`, `Опция "Копировать"`, `Модальное окно настроек виджета (+)`, `Список чатов (+)`, `Поле ввода текста`, `Чекбокс "Уведомления"`, `Тугл "Звуковые уведомления"`.

Если проверяется именно вид элемента на экране (в т.ч. кнопка/поле в конкретном визуальном состоянии) — допустимо и предпочтительно: `Отображение кнопки "Отправить"`, `Отображение поля ввода текста`.

## Роли и авторизация: порог ≥ 70 %

Дели первый уровень по авторизации/ролям **только если различия существенны**.

Формула:

```text
% отличий ≈ (число элементов, которые есть/выглядят/доступны иначе) / (общее число элементов в более полной ветке) × 100
```

Правила:

- **≥ 70 %** → создавай отдельные ветки (`Неавторизованный пользователь (+)`, `Авторизованный пользователь (+)`, `Родитель (+)`, `Ученик (+)`, `Сотрудник (+)` — только те, что есть в документации).
- **< 70 %** → не дублируй дерево: одна общая (самая полная) ветка + блок `Дельта для роли "<Роль>" (< 70% отличий)` или точечные пометки.
- Ветку «Неавторизованный» создавай только если у него собственный отдельный UI фичи и отличие ≥ 70 %. Если доступа нет — ветку не создавай.
- Роли, которых нет в документации, не добавляй.
- Если роль не определена — `Авторизованный пользователь` без дробления.
- 1–3 точечных отличия (лимит времени, один тип чата, одно уведомление) — это всегда дельта, а не отдельное дерево.
- Один элемент дублируй в нескольких ролевых ветках только если ветки уже созданы по порогу.

### Пример дельты

```text
Авторизованный пользователь / Участник чата (+)
	-…общее дерево…

Дельта для роли "Родитель" (< 70% отличий)
	-Нет элемента списка "Чат класса"
	-Отображение уведомления о бане ребёнка-ученика
```

## Что НЕ нужно (исключения)

В декомпозицию **не попадают**:

- API, backend, SQL, внутренняя реализация, алгоритмы, события, сценарии, тест-кейсы;
- валидация полей; правила обязательности, уникальности, допустимой длины, формата и маски ввода;
- сообщения, тексты, коды и экраны ошибок;
- результаты неуспешных действий, связанные с ошибками или валидацией.

Визуальные состояния учитывай только если они **не** связаны с валидацией или ошибкой.

Итог — исключительно структурная декомпозиция пользовательского функционала.

## Критерий готовности

QA может построить блок-схему, увидеть уровни, определить, что требует детализации, и использовать дерево как основу покрытия.

## Чек-лист этапа «Иерархия»

- [ ] Глубина задана табуляцией + дефисами; символы дерева отсутствуют.
- [ ] Все контейнеры помечены `(+)`, конечные элементы — без пометки.
- [ ] Каждый уровень содержит только непосредственных потомков; раскрытие полное.
- [ ] Отображаемые элементы именованы через «Отображение …»; интерактив и контейнеры не переименованы.
- [ ] Разные сущности не объединены; разные типы объектов списка выделены отдельно; уровни не смешаны.
- [ ] Роли разделены только при ≥ 70 %, иначе оформлена «Дельта».
- [ ] В дереве нет валидаций, ошибок, API/backend, сценариев, тест-кейсов.
